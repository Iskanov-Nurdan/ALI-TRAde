# Система учёта движения машин, рейсов и расходов

Внутренняя система учёта: откуда и куда вышла машина, кто отправил, кто принял,
уложилась ли в срок и какие расходы возникли по конкретному рейсу.
GPS не используется — состояние определяется действиями сотрудников.

**Стек:** Python 3.12 · Django 5 · Django REST Framework · JWT · PostgreSQL (SQLite для разработки)
· фронтенд на HTML/CSS/JavaScript без фреймворков.

---

## Структура проекта

```
backend/                 Django-проект (слои: views → services → repositories → models)
  config/                настройки, маршруты, wsgi
  apps/
    core/                базовые классы, аудит, health-check, пагинация, ошибки
    accounts/            сотрудники, роли, JWT-аутентификация
    points/              справочник точек
    deliveries/          рейсы, история событий, автопросрочка
    expenses/            расходы, типы расходов, правило плательщика
    reports/             отчёты и выгрузка CSV
frontend/                статичный интерфейс (HTML + CSS + JS-модули)
nginx/                   конфигурация обратного прокси
docker-compose.yml       БД + API + nginx
```

Бизнес-логика находится **только** в слое `services`, доступ к данным — в `repositories`,
представления занимаются валидацией входных данных и вызовом сервисов.

## Быстрый старт (разработка)

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows; на Linux: source .venv/bin/activate

pip install -r backend/requirements.txt
cd backend
copy ..\.env.example ..\.env      # Linux: cp ../.env.example ../.env
```

Учётные записи после `seed_demo` (пароли задаются переменными `ADMIN_PASSWORD` и `DEMO_PASSWORD`,
по умолчанию `admin12345` / `employee12345` — **обязательно смените в бою**):

| Логин | Роль | Назначение |
| ----- | ---- | ---------- |
| `admin` | Администратор | полный доступ |
| `employee3`, `employee5`, `employee7` | Сотрудники | обычные права |

## Запуск в Docker

```bash
cp .env.example .env        # заполните пароли и DJANGO_SECRET_KEY
docker compose up -d --build
docker compose exec api python manage.py seed_demo
```

Имя проекта задано в `docker-compose.yml` (`name: delivery-tracker`): имя каталога с кириллицей
Compose использовать не может — без этого он завершается с ошибкой `project name must not be empty`.

Интерфейс: http://localhost/ · API: http://localhost/api/ · health-check: http://localhost/health/

Nginx отдаёт статику фронтенда, проксирует `/api/`, ограничивает частоту запросов
(вход — 5 запросов в минуту, API — 20 запросов в секунду), включает gzip и заголовки безопасности.

## Ключевая логика

**Срок прибытия.** Задаётся двумя способами: количеством часов (`duration_hours` + `duration_minutes`)
или конкретным временем (`deadline_at`). В базе всегда хранится рассчитанный `deadline_at`.
Если срок задавался длительностью, при подтверждении отправления дедлайн пересчитывается
от фактического времени выезда.

**Просрочка.** Определяется автоматически: `статус = В пути` и `текущее время > deadline_at`.
Отдельного поля в базе нет. Факт просрочки записывается в историю событием `DEADLINE_PASSED`
один раз — при обращении к спискам или командой `python manage.py sync_overdue` (её удобно
повесить на cron, если нужна фиксация без активности пользователей).

**Позднее прибытие.** Подтверждение прибытия не стирает факт просрочки: событие остаётся
в истории, а система считает опоздание (`late_minutes`) как разницу между фактом и планом.

**Цвет строки.** Не хранится в базе, вычисляется: просрочен → **красный**, есть расход →
**оранжевый**, красный имеет приоритет.

**Маршрут.** Помимо точек отправления и прибытия у рейса может быть до десяти промежуточных
точек (граница, склад, перегруз) в заданном порядке. Прохождение каждой отмечает любой сотрудник —
в истории появляется событие `WAYPOINT_PASSED` с временем и фамилией. Убрать из маршрута точку,
прохождение которой уже отмечено, нельзя.

**Расходы.** Привязываются к конкретному рейсу (не к номеру машины), добавляются в любой момент —
до отправления, в пути, после просрочки и после прибытия. У рейса может быть неограниченное число
расходов от разных сотрудников; итоги считаются отдельно по каждой валюте.

**Правило плательщика.** Настраивается администратором (раздел «Справочники»): порог суммы, валюта
и плательщики выше и ниже порога. Применяется, только если сотрудник не выбрал плательщика вручную.

## Основные эндпоинты API

Аутентификация — JWT: `Authorization: Bearer <access>`.

| Метод и путь | Назначение |
| ------------ | ---------- |
| `POST /api/auth/login/` | вход, выдача access/refresh |
| `POST /api/auth/refresh/` | обновление access-токена |
| `GET /api/auth/me/` | текущий пользователь |
| `GET/POST /api/deliveries/` | список рейсов с фильтрами, создание |
| `GET /api/deliveries/dashboard/` | сводка для панели |
| `GET /api/deliveries/{id}/` | карточка рейса с расходами, комментариями и историей |
| `POST /api/deliveries/{id}/dispatch/` | подтверждение отправления |
| `POST /api/deliveries/{id}/receive/` | подтверждение прибытия |
| `POST /api/deliveries/{id}/cancel/` | отмена рейса |
| `POST /api/deliveries/{id}/waypoints/{wid}/pass/` | отметка прохождения промежуточной точки |
| `GET/POST /api/deliveries/{id}/comments/` | комментарии |
| `GET /api/deliveries/{id}/events/` | история действий |
| `GET/POST /api/deliveries/{id}/expenses/` | расходы рейса |
| `GET /api/vehicles/search/?q=1234` | поиск рейсов по номеру машины |
| `GET /api/expenses/`, `/api/expenses/totals/` | реестр расходов и итоги |
| `GET/PUT /api/expenses/settings/` | правило плательщика (изменение — админ) |
| `GET/POST /api/points/`, `/api/users/`, `/api/expense-types/` | справочники (изменение — админ) |
| `GET /api/reports/summary/`, `/expenses/`, `/employees/` | отчёты (админ) |
| `GET /api/reports/export/deliveries/`, `/expenses/` | выгрузка в Excel; `?ext=csv` — CSV (админ) |
| `GET /api/audit/` | журнал действий (админ) |
| `GET /health/` | health-check |

Фильтры рейсов комбинируются: `date_from`, `date_to`, `vehicle_number`, `point_from`, `point_to`,
`dispatched_by`, `received_by`, `status`, `has_expenses`,
`state` = `active` / `in_transit` / `overdue` / `arrived` / `arrived_late` / `arrived_on_time`.

## Безопасность

- `DJANGO_SECRET_KEY` обязателен при `DJANGO_DEBUG=False` — без него приложение не стартует.
  В режиме разработки ключ генерируется автоматически.
- `DJANGO_DEBUG` и `CORS_ALLOW_ALL_ORIGINS` по умолчанию выключены.
- Вход ограничен по частоте (`THROTTLE_LOGIN`, по умолчанию 20 запросов в минуту с адреса),
  анонимные запросы — `THROTTLE_ANON`.
- За обратным прокси включите `TRUST_PROXY_IP_HEADER=True` и `NUM_PROXIES=1`, иначе адрес клиента
  берётся из прямого соединения. Заголовок `X-Forwarded-For` без этой настройки игнорируется,
  значение всегда валидируется перед записью в журнал аудита.
- Выгрузки обезвреживают формулы: значения, начинающиеся с `=`, `+`, `-`, `@`, получают префикс `'`,
  поэтому Excel открывает их как текст.
- Текстовые поля не принимают HTML-разметку и ограничены по длине.

## Эксплуатация

- Все важные операции пишутся в журнал аудита (`/api/audit/`) и в лог приложения.
- Секреты хранятся в `.env` в корне проекта, пример — `.env.example`.
- Для фиксации просрочек без пользовательской активности: `python manage.py sync_overdue`.
- Часовой пояс по умолчанию `Asia/Bishkek`, задаётся переменной `DJANGO_TIME_ZONE`.
- Внешний доступ через туннель (ngrok и подобные): добавьте домен в `DJANGO_ALLOWED_HOSTS`,
  `CSRF_TRUSTED_ORIGINS` и `CORS_ALLOWED_ORIGINS`, затем `docker compose up -d --build api`.
- Значения в `.env` не должны содержать `$` — docker compose подставит переменную окружения.
- Отчёты выгружаются в `.xlsx` (закреплённая шапка, автофильтр, подобранная ширина колонок);
  CSV остаётся доступен параметром `?ext=csv`.
- Интерфейс переключается между светлой и тёмной темой кнопкой в верхней строке; выбор
  запоминается в браузере, при первом входе берётся системная настройка.
